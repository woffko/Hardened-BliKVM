# Work plan after the final GUI comparison (2026-09-26)

Hardened BliKVM is an administration device for local hardware. The operator
decided on 2026-09-26 that reference features are to be available, with the
risky ones switched off by default in the settings, instead of being removed:

- Terminal (KVM shell and serial port terminal) and Scripts: available, off by
  default, switched on in the settings.
- Remote ISO download and the PicoClaw AI assistant: available, off by
  default, switched on in the settings.
- SSH: an on/off switch in Device settings, as in the reference.
- Tailscale: the same actions and views as the reference (install state,
  login, logout, start, stop, status), not a read-only view.
- USB wakeup: not needed now; recorded as declined.
- The mobile layout must be compared with the reference as well.

Baseline: board on native profile, application slot 26 (source `6388044`
lineage), update runtime 0.1.0~dev19, reference Hardened NanoKVM 2.0.42 at
10.0.87.133. The reference GUI password equals the board's GUI secret
(project-memory record `e9d86cb1-f18e-413b-afc8-618db6bcb861`).

## Rules for every phase

- Server-side enforcement: a switched-off feature is refused by the server and
  the owner, not only hidden in the GUI. Settings are persisted by the owner,
  default off, and survive restarts and updates.
- Privileged work runs in the board owner or a dedicated socket-activated
  helper with a closed protocol, never in the network-facing server.
- Every change ships as a signed application slot (and, when system files
  change, a new update runtime package) installed through the API, and is
  verified on the board with a probe or API read-back.
- Tests in `scripts/check.sh` stay green; the audit
  (`docs/baselines/corrective-parity-audit-20260920.md`) and design docs are
  updated per phase.
- Operator-dependent steps stop with a precise request instead of guessing.

## Phase A: settings-gated administration features

1. Design note (`docs/design/admin-features-v1.md`): persisted feature
   switches in the owner, the privilege boundary of each feature, limits,
   audit logging, capability advertisement and the reference wire contract.
2. Feature switches: owner-persisted, default off; capability manifest
   advertises each feature as available/switched-off/switched-on; Appearance
   settings expose the switches exactly as the reference does.
3. Terminal: KVM shell and serial port terminal over the reference WebSocket
   contract, through a dedicated helper, one session per operator session,
   refused while switched off.
4. Scripts: upload, list, delete, run and autostart as the reference does,
   stored and executed by the helper, refused while switched off.
5. Remote ISO download and local image upload into the virtual media store,
   with size limits, HTTPS/HTTP URL validation, progress and cancellation,
   refused while switched off; the upload path is always available.
6. PicoClaw assistant: port the reference feature, off by default, with the
   API key stored by the owner and never returned to the GUI.

Acceptance: each feature works on the board when switched on, is refused by
the server with it switched off, defaults to off after a fresh image, and the
parity walk shows the reference menus and settings.

## Phase B: device and network settings parity

1. SSH on/off in Device settings (owner enables/disables and reports the
   OpenSSH service state).
2. Tailscale as in the reference (install state, login URL, logout, up/down,
   status) through the owner.
3. KVM self-reboot in Device > Advanced, with confirmation.
4. System > Network: IPv4 DHCP/manual configuration and interface details
   (address, mask, router, DNS) through the owner.
5. About: IP addresses (from the owner) and the system image version.
6. Session lock persisted across server restarts.
7. Virtual media: USB gadget reconnect.
8. Screen: MJPEG frame detect (mapped to the streamer's duplicate-frame drop).
9. Diagnostics: observed HID, power and virtual media component states.
10. USB wakeup: declined by the operator; documented.

Acceptance: each item verified on the board by API read-back or a browser
probe, and absent from the remaining-gaps list of the parity walk.

## Phase C: mobile layout parity

1. Extend the text parity walk to the mobile layout (Pixel 7 profile): every
   toolbar menu, settings tab and the mobile-only controls (local keyboard,
   trackpad, cursor overlay).
2. Fix differences; the operator re-checks on the phone.

Acceptance: desktop and mobile parity walks list only documented, operator-
approved differences.

## Phase D: firewall on the device (operator-gated)

Requires a recovery path before starting (UART console, physical access or a
card with the current image). Migrate the legacy iptables rules, enable the
owned nft table, then apply each mode and verify HTTPS, DHCP, Tailscale and
WebRTC over IPv4 and IPv6, with rollback verified.

## Phase E: images and system updates

1. SD image rebuilt from the final board state; the operator verifies the
   card boots (operator-gated).
2. RAW system update: design, signed RAW payload from the same build as the
   card image, partition writer with read-back and recovery; host tests, then
   a device test on a spare card (operator-gated).

## Deferred by the operator

Automatic Windows keyboard layout switching; H.264.
