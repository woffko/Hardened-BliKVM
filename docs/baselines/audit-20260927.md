# Pre-release audit (2026-09-27)

Before the first alpha the operator asked for a code audit and a working
check of the GUI; they reported that ISO upload and mounting did not work.
Board: the test board on the card from plan phase E1, slot 46
(`0.1.0-dev42`), update runtime `0.1.0~dev30`. Raw receipts stay under
`evidence/private`; this file names them.

## Method

- GUI walk on the board, desktop and mobile
  (`tools/playwright/gui_walk_device.mjs`): every menu popover opened and each
  submenu hovered, every dialog and settings tab and System section opened;
  nothing inside clicked. Every `/api` answer, console and page error
  recorded (`gui-walk-desktop-*.json`, `gui-walk-mobile-*.json`).
- Virtual media through the GUI as an operator uses it
  (`tools/playwright/media_gui_device_test.mjs`): a small ISO uploaded from
  the Download menu, mounted as a CD-ROM, checked through the API, unmounted
  and deleted, desktop and mobile (`media-gui-*.json`).
- VP8 WebRTC received and decoded (`vp8-audit-*.json`).
- Latency of a request on the board owner's shared lock (the lock HID reports
  take) while other pages load (`owner-lock-latency-20260927.txt`), and the
  latency of every GET the GUI makes.
- Static checks: every web API call matched against the server's routes and
  traced to the component that renders it; route authentication and CSRF
  coverage; `unwrap`/`expect`/`panic!` on request paths; `TODO`/`FIXME`;
  RustSec advisories (`cargo audit`, local database of 2026-09-25) for the
  217 Rust dependencies.
- Board state that the SD image builder carries into an image.

## Findings

Severity: **high** breaks a feature or leaks state to another user of the
image; **medium** misleads the operator or risks a stall; **low** is
hygiene.

### High

H1. **Uploads cannot be stored on a card built by the image builder.** The
image's MSD partition (p3) is created with its root directory owned by
`root:root`, mode 0755. `/etc/fstab` mounts it with
`x-systemd.requires=systemd-tmpfiles-setup.service`, so the tmpfiles rule
that gives the directory `0770 root:hardened-blikvm` runs on the empty
mount point before the mount and never on the partition. The server (and
the remote-download helper, same user) cannot create files there: the
Download menu shows "service unavailable" (HTTP 503) for every upload
(`media-gui-before-fix-*.json`). After setting the partition root to
`0770 root:hardened-blikvm` by hand during this audit, upload, CD-ROM mount,
unmount and delete all passed on desktop and mobile
(`media-gui-after-perm-*.json`, `media-gui-mobile-*.json`).

H2. **Catalog entries outlive their files.** The image builder copies the
source board's `/etc/hardened-blikvm-gadget/catalog.json`, while the image's
p3 is empty. The card listed `kubuntu.img` without a file; mounting it failed
in the owner with `ImageMissing` and the dialog said only
"backend_rejected". The server never reconciles the catalog with the image
store.

H3. **HID stalls for about 1.5 s while Settings > Network or About load.**
`GET /api/network/dns`, `/api/network/ipv6` and `/api/vm/info` each take
1.3-1.4 s (about nine `nmcli` runs for two connected interfaces) and run
inside the owner's shared state. While they load, a request on that lock took
a median of 1429 ms (max 1554 ms) against 17 ms idle. The TLS state then
missed the server's 5-second control deadline once in the walk
(`GET /api/vm/tls` 503, the HTTPS row failed to load).

H4. **The root password does not follow the web account.** The reference
(`server-rust/src/api/account.rs`) runs `passwd root` with the new password on
its first setup and on every password change, before it stores the account,
and its password page warns that both the web and the root (SSH) password
change. Here root keeps the image default (`1234`, expired) and the page no
longer shows the warning. A draft (administration helper `chpasswd` with the
password on standard input, server calls before the account is stored) is
parked in `git stash` as `root-password-parity-draft`.

H5. **An SD image carries the source board's state.** Besides the catalog
(H2): the administration switches (`admin-features.json`; on the test board
remote download and RAW system updates are on), the confirmed firewall mode,
the owner's gadget, media, ATX and HID journals, the system-action journal
with an unreconciled reboot (the first API reboot on a new card is refused
with `pending_unreconciled`), and leftovers: kvmd unit backups, a 1 MB copy of
an old web build, configuration backups.

### Medium

M1. The TLS certificate's SHA-256 fingerprint is always empty: the owner
parses `SHA256 Fingerprint=`, OpenSSL 3 prints `sha256 Fingerprint=`.

M2. Media feedback: a click within the owner's cooldown between media
commands shows `cooldown_active` as an error; a CD image under 300 sectors
(the kernel's minimum, `ETOOSMALL`) and a missing file both show
`backend_rejected`; a storage failure shows "service unavailable".

M3. An upload replaces an image of the same name while it is attached: the
new file is renamed over the attached one, the target keeps the old content
and the catalog describes the new.

M4. `nmcli` runs in the owner without a timeout (`NmcliRunner::nmcli` waits for
the process indefinitely); a stuck NetworkManager would hold the owner, and
with H3 the HID lock.

M5. The capability manifest reports `signedSystemUpdates` unavailable while
RAW system updates are switched on and served.

M6. `scripts/check.sh` fails intermittently when the build host is loaded:
timing tests with 50-150 ms or 5-second windows (four were widened on
2026-09-27) and the GUI parity self-test's page-load cap.

M7. Thirty-odd functions in `web/src/api` call routes the server does not
have (HID paste, reset, mode and USB wakeup; time set and sync; system-log
settings; autostart writes; GPIO, HDMI, OLED, swap, memory limit, virtual
devices; preview, offline and system-update checks; the Wi-Fi AP login;
the remote-download switch). Capability gates hide every control that calls
them today, so none is broken in the GUI, but a gate change would expose
broken controls and nothing checks it.

### Low

L1. `GET /api/network/wifi/scan?rescan=true` has a side effect.
L2. Until First Setup, whoever reaches the board creates the account (and,
with H4, root's password), as in the reference; set a new board up on a
trusted network.
L3. The web dependencies were not audited (needs the npm registry).
L4. The update runtime package can change only with a RAW system image or by
hand; the API installs application slots only.
L5. Parity backlog, read-only or absent here but writable in the reference:
time and NTP settings, the remote system log, autostart editing, OLED
settings.

## Verified working

- Every menu, dialog, settings tab and System section opens without an API
  error or page error on desktop and mobile, except the TLS row (H3).
- Upload, CD-ROM mount, unmount and delete through the GUI, desktop and
  mobile, once the image store is writable (H1).
- VP8 WebRTC: a 1920-pixel-wide frame decoded, 657 KB received.
- Firewall page and Wi-Fi (plan `work-plan-20260927-firewall-wifi.md`,
  checked the same day).
- Authentication: only `/health`, `/capabilities`,
  `/application/current-version`, `/auth/setup` and `/auth/login` are public;
  every other route needs a session, and state-changing methods a CSRF token
  and a matching Origin.
- No RustSec advisory applies to the locked Rust dependencies; no `TODO` or
  `FIXME`; no `unwrap` or `expect` on request input in the server, owner or
  administration helper.

The fix plan is `docs/baselines/work-plan-20260927-alpha1.md`.

## Fixes verified on the board (2026-09-27)

Plan `work-plan-20260927-alpha1.md`, slot 47 (`0.1.0-dev43`, commit
`ddd1e1e`) and update runtime `0.1.0~dev31`:

- H1: the SD image builder now gives the MSD partition's root `0770
  root:hardened-blikvm` and mounts it after tmpfiles (for new cards; the test
  board's partition root was corrected by hand during the audit). Uploads,
  CD-ROM mounts, unmounts and deletes pass through the GUI on desktop and
  mobile (`media-gui-seq47-{desktop,mobile}-*.json`).
- H2: a catalog entry whose file was removed on the board disappeared at the
  next catalog read, with the server logging "dropped the catalog entry"
  (`media-stale-seq47.txt`); new images start with an empty catalog.
- H3: a request on the owner's shared lock took a p90 of 20 ms (max 21 ms)
  while DNS, IPv6 and About loaded in a loop, against 1488 ms before; the
  network reads themselves answered in 15 ms from the shared reading
  (`owner-lock-seq47-*.json`). The GUI walk passed on desktop and mobile
  with no API or page error, the TLS row included (`gui-walk-seq47-*.json`).
- H4: root's password follows the web account at First Setup and on every
  password change; the password page shows the reference's warning. The
  operator changed the web password on the board on 2026-09-28: the helper
  logged "root password changed", root then logged in over SSH with the web
  password, and `chage` reported the change that day and no expiry.
- H5: the builder resets the source board's switches, confirmed firewall
  mode, owner journals and backups (`tools/test_build_sd_image.py`); checked
  again on the alpha image.
- M1: the certificate fingerprint is read (`sha256 Fingerprint=` of OpenSSL
  3).
- M2, M3 (`media-api-seq47-*.json`): a 44 KiB ISO as a CD-ROM is refused
  with `image_too_small`; an upload over the attached image is refused (409,
  "detach the drive before replacing its image"); a remote download of an ISO
  served on the board completed; the dialog waits out the owner's pause.
- M4: every `nmcli` run in the owner is bounded.
- M5: the manifest reports RAW system updates with the administration
  helper.
- M6: four timing tests and the GUI parity self-test have room on a loaded
  host; `check.sh` passed three times in a row since.
- M7: `tools/test_web_api_routes.py` fails on an unrouted web call that no
  named gate hides.
- L1: a Wi-Fi rescan is a POST; the scan found three networks
  (`wifi-seq47-*.json`).
- Also passed: firewall page status in Baseline, VP8 (a 1920-pixel-wide
  frame decoded) and the settings writes set back to their values: session
  lock, mDNS, hostname, frame rate, system-log test message, SSH switch,
  scripts (`firewall-status-seq47-*`, `vp8-seq47-*`, `safe-writes-seq47-*`).

## Found after the first publish (2026-09-28)

H6. **The image store is too small, and an upload that does not fit fails
without a reason.** The SD image gives virtual media about 2 GiB (p3 after a
12 GiB root and 14 GiB of data), and one upload may have at most 4 GiB. The
operator's ISO, larger than both, reached about 20 % in the Download dialog
and started over: the server refused the declared length at once, nginx
(which passes the body on unbuffered) logged `writev() failed (32: Broken
pipe) while sending request to upstream` and went on receiving the body, and
the browser saw only the connection drop. A 1.2 GB FreeBSD ISO then did the
same: its 68-character name was over the upload's 64 (the catalog and the
remote download allow 128), and the server's refusal did not reach the
operator's browser. Cancel could not stop it: the dialog polls the remote
download's status, which knows nothing of an upload and answers "idle", and
that answer marked the running upload complete after 2.5 s and hid Cancel;
only a page reload stopped the transfer. The first
publish of `v0.1.0-alpha.1` (slot 49, SD image `90bd7320...`) was withdrawn
the same day.

Fix (plan phase I): the data partition shrinks to 8 GiB (a RAW system update
needs about 5 GB there) and the first boot grows the image store to the end
of the card; one image may have 64 GiB; the server reports the store's free
space and refuses what does not fit, by its declared length and when a write
runs out of space; the Download dialog shows the free space, refuses a
file that does not fit and asks the server's new upload check (name, size,
free space, attached image) before sending; names may have 128 characters;
the remote download's status no longer ends an upload, and Cancel takes the
upload button's place while a file is sent. The test board's card (64 GB) had
31 GiB unused after p3: p3 was grown in place (table saved first), giving a
33 GiB store.

L6. Settings > Device listed "Autostart Scripts Settings" (a read-only list
of the owner's autostart scripts with a link to the network settings), which
the reference 2.0.42 does not show; the operator took it for the scripts
switch, which both keep in Appearance > Menu Bar > Scripts. The entry is
removed.

M8. The mouse trailed the hand further the longer it moved. Every HID
report is one HTTPS request, sent after the previous one finished, and the
web client queued a mouse report every 10 ms; a request that took longer let
the queue grow. The reference sends each report as a WebSocket message
without waiting. Fixed: at most one mouse report is in flight, and movement
meanwhile merges into one pending report (`MouseQueue`), so the cursor
trails by one request. On slot 55 a report's round trip took 12 ms at p50
and 15 ms at p90 (40 ms at most) while an MJPEG viewer played
(`hid-latency-seq55-*`, `tools/device/hid_latency_probe.py`), under the
40 ms that would have moved HID onto a WebSocket like the reference's.

M9. Video is not smooth. MJPEG passes the capture through at 1920x1080 and
up to 66 frames/s, 150-260 KB a frame (about 80 Mbit/s for one viewer); on a
slower link frames wait in the socket buffers between the capture and the
browser, and the picture (and the target's cursor in it) falls seconds
behind. VP8 decodes, converts and encodes 1080p in software at about 10
frames/s (54, 27 and 77 ms a frame), and the encoder runs whether or not
anyone watches VP8: it took 2.3 of the four cores while the operator watched
MJPEG. The H616's video engine decodes only under the mainline kernel (no
hardware H.264 encoder), so H.264 means software x264. Open: plan phase J.

L7. Sessions last 15 minutes from login whatever Settings > Device >
Session lock after says (the reference issues them for that duration).
Fixed in slot 53: a session lives as long as the setting, and changing it
retimes the caller's session.

Checked on slot 55 (2026-09-28): the GUI walk on desktop and mobile with no
API or page error, the firewall page status, Wi-Fi status and scan, the
safe writes set back, the owner's shared lock at 15 ms p90 while the network
pages load (`gui-walk-seq55-*`, `firewall-status-seq55-*`, `wifi-seq55-*`,
`owner-lock-seq55-*`, `safe-writes-seq55-*`); VP8 at 1920x1080 decoded
(`vp8-webrtc-seq55-key-*`); M9's MJPEG and CPU numbers in the plan's phase J
status.

## Release 0.1.0-alpha.1 (2026-09-28)

The first publish was withdrawn after H6. The rebuilt pre-release (tag at
`b9c89d1`, 2026-09-29) carries the SD image built from the slot 55 board
(8 GiB data, an image store grown to the end of the card at first boot;
sanitization checks passed and the image read back), `SHA256SUMS`,
`IMAGE-INFO.txt` and the signed application bundle of slot 55 (from
`6b53430`); the published files' digests match the local ones. The board
ends with every administration switch off and the firewall in Baseline.

Media on slot 55 with the operator's drive attached (the test left it alone
and never opened the image dialog, where a click would swap the drive;
`media-gui-seq55-{desktop,mobile}-nomount-*`): on desktop and mobile a
40 GiB file was refused before sending ("does not fit: the image store has
30.3 GiB free"), a name with a space was refused by the server's check
before sending, Cancel stayed in view and stopped a 3 GiB upload, a 5 GiB
ISO with a 91-character name was uploaded and then deleted, and the
operator's drive was still attached afterwards. Mounting that ISO as a
CD-ROM waits for the drive.
