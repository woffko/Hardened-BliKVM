# Release 0.1.0-beta.3: VP8 drawn as MJPEG, system actions that no longer lock up, and the RAW update on the test board (2026-10-07)

The colour work of 2026-10-06 (`audit-20261006-colour-range.md`) left VP8
drawn darker than MJPEG and the fixed encoders on no published card. The
operator asked whether VP8 could have a constant correction instead of a pass
over every frame, and for a release with the card image and a RAW system
bundle of the same build, the RAW bundle checked by installing it on the test
board. Doing so found that system actions locked up for good after one
reboot from the page; with the operator's answers that was fixed in this
release too, so the release is slot 78, after slots 76 and 77 on the way.
Receipts are under `evidence/private/beta3-20261007` (not in Git), the
probes' under `evidence/private/beta3-slot7*` and
`evidence/private/raw-system-update-beta3-20261007-*`.

## VP8 drawn through a table in the page

VP8 has no field for what its samples mean, and Chromium draws a VP8 frame as
of the narrow range with the BT.601 matrix: every channel of the board's
full-range samples comes out as 255/219 (level - 16). Converting the samples
on the board would be a pass over every frame there. The page instead draws
the VP8 picture through an SVG `feComponentTransfer` table that undoes the
stretch per channel (`9ae860b`, `web/src/lib/vp8-range.ts`): the levels 17
to 234 come back within one, black and white stay so, the colours 2 % less
saturated than MJPEG's (the two ranges' chroma scales differ). H.264 over
the same view is not filtered.

The browser applies a filter as it draws every frame. Measured on the host
with Chromium drawing in software (SwiftShader), a 1920x1080 track at 30
frames a second in a picture of that size, 15 s per run, alternated three
times (`filter_cost.mjs`): the browser's processes used 23 % of a core
without a filter and 120 % with the table, and drew 25.8 frames a second of
30.3. A colour matrix (`feColorMatrix`) and CSS `contrast()` `brightness()`
cost the same (119 % and 124 %, 29.4 and 29.1 frames): what costs is the
filter pass, not the table. With the machine's GPU the pass is a texture
lookup in the compositor, so the page applies the table only where WebGL
names a renderer that is not a software rasterizer; no WebGL, SwiftShader,
llvmpipe, softpipe or Microsoft's Basic Render Driver leave VP8 as before.
Not measured: a browser with a GPU (none on this host), Firefox and Safari.

Tests: `tools/test_vp8_range.mjs`, and `tools/playwright/vp8_range_contract.mjs`
(the built page given a track of the board's samples marked as Chromium marks
a decoded VP8 frame: greys within 1 level of the JPEG, colours within 3, 20
levels off without the table; H.264 over the same view unchanged; VP8 as
before in the headless Chromium that draws in software). The contract failed
without the filter.

MJPEG frame each screenshot looks most like, twelve screenshots, all matched,

## The switches across a RAW system update

Found while preparing the RAW bundle: the RAW update writes a new root and
carries a fixed list of paths (`CARRIED_STATE` of
`bli-kvm-system-raw-update`), and the list that runs is the board's own
update runtime's, `0.1.0~dev36` on every published card. Four of the board's
settings are not state files but system configuration: the enablement of the
OpenSSH server, of the QUIC gateway and of the Tailscale daemon, and mDNS in
`/etc/systemd/resolved.conf`. None is in the list, so a RAW update left them
as the new image has them (the OpenSSH server and the Tailscale daemon on, the
gateway and mDNS off), whatever the operator had set. The page's System
Update section says that switches are carried over. Not carried either: the
application stores of that runtime, `/var/lib/hardened-blikvm-slots-v2`,
`-update-v2` and `-exec-ledger` (the v1 stores and `-exec` are), and root's
home apart from `.ssh`.

Changed (`bf0f0ce`): the board owner, which comes with the application slot,
records the four with the system image they were recorded under
(`/etc/hardened-blikvm-image`) in its state directory, which the list
carries (`system-switches.json`). At its start, under another image than the
record names, it sets them as recorded and records the new image; under the
same image the record follows the board, so the owner never undoes a change
made otherwise. Its own changes are recorded at once, the Tailscale daemon's
enablement whenever it reads it. The SD image builder leaves the record out
of a new card. Nothing changes in the update runtime, so this works on the
published cards once their application is this release's. The application
stores are left for the next update runtime; the release notes have a board
install the application bundle before the RAW bundle, so that the image's
stores and the board's protected copies agree. Tests: seven of the keeper, one
of the owner's dispatch (it failed without the record's update after a
change), the image builder's test of the source board's reset state (it
failed before the record was left out).

On the test board, slot 76 made the record at its first start: SSH, QUIC and
the Tailscale daemon on, mDNS off, under the board's image name
`Hardened BliKVM H616 SD image 2026-09-26`; nothing else of the board's state
changed (`state-before-slot76.json` against `state-slot76.json`).

## A reboot from the page blocked the next one

The first RAW install on the test board (below) uploaded and staged the
bundle, and the install was refused: `{"applied": false, "rejection":
"pending_unreconciled"}`. The system-action journal held a reboot dispatched
on 2026-10-03 13:02, during the hardware H.264 work, that had never been
accepted, and a pending record refuses every further action. The operator had
tried to close it by hand. Nothing in the shipped product could: the
acceptance unit's program cannot open the journal while the board owner runs
(the store keeps an exclusive lock on its directory as long as it is open, and
the owner keeps it open: `StoreBusy`), and the owner's own `accept_post_boot`
request has no caller in the server or the page. Every board that rebooted
once from the page (Device > Reboot, a RAW install or rollback) refused every
later system action, power cycles included. With the operator's answer the
record was closed as the device gate does it, by that request on the owner's
control socket as root (`accept-post-boot-before-raw.txt`: `applied`), and the
install went on.

Changed (`eee16df`, in the application slot): before the owner prepares a
confirmed action, a single pending record is accepted with the guards
attested, the operator's confirmation being their word that the board came
back; the policy accepts only a record from another boot past the startup
guard, so one dispatched in the current boot still refuses (test
`the_next_confirmed_action_closes_the_reboot_that_happened`, which failed
without it). On the test board, slot 77 (`9abeddb`) replaced slot 76 with
the RAW install's own reboot pending in the journal; a reboot through the
page's action (`raw-system-update-beta3-20261007-reboot-fix.json`) was then
applied, where it had been refused, and the board came back in 62 s with its
state the same (the temporary IPv6 addresses apart). Found and left: the owner
gives the policy the wall clock for an
action and the uptime for an acceptance, so the 60 s cooldown after an
accepted action never holds a new one (`docs/design/system-actions-v1.md`).

Two more ways to the same refusal, found reading the journals the card images
carry (`journal_read.py`, the store's layout): the journal has sixteen places
and gave none up, so the sixteenth system action was a board's last (the test
board had nine records); and the SD image builder copied the source board's
journal to new cards. beta.1's image carried the test board's eight records,
the last of them the reboot of 2026-10-03 still dispatching, so every beta.1
card refused its first reboot from the page and its RAW install with
`pending_unreconciled` (the beta.3 application lets the first confirmed action
accept that record, whose boot is another). With the operator's answer both
were changed in this release: a full journal makes room in the place of the
oldest record that settled in an earlier boot (`1fbdd49`, test
`a_full_journal_gives_up_the_oldest_record_of_an_earlier_boot`, which failed
without it), and the image builder leaves the journal out of new cards
(`5753af5`, test `test_a_new_card_has_an_empty_system_action_journal`). A new
card's owner initializes an empty journal at its first start; that path ran on
the test board when its journal was first made (2026-09-18), not yet on a card
written from this image.

## The RAW system update on the test board

Installed twice, each bundle built from the root of the card image made from
the board it went to.

The first, `hardened-blikvm-system-0.1.0-beta.3-seq3.tar` (slot 76's build),
went to the board as it was in the morning: slot 76, update runtime
`0.1.0~dev36`, the image name of 2026-09-26. Upload and the board's
verification took 6.5 minutes, the write and the new boot 34.6
(`raw-system-update-beta3-20261007-install-2.json`); it came back `booted`
with the new image name and was confirmed. Compared with before
(`state-before-raw-2.json`, `facts-before-raw-2.txt` against `-after-raw`):
the same account, administration features (RAW on), firewall mode, screen
settings and engine choice, QUIC on and active (the image has it off: the
owner set it as recorded, "switches set as before the new image" in its
journal 43 s into the boot), SSH on, mDNS off, Tailscale state, host name,
autostart, jiggler, time settings, DNS, IPv6 settings, Wake-on-LAN, saved
Wi-Fi, session lock, image store and catalog, the slots, and on the system the
machine id, the four SSH host keys, the TLS certificate, the units, the
encoder `a09d9750`, the runtime and the kernel. Different, as expected: the
image name and the record's image, the RAW record, the uptime, the temporary
IPv6 privacy addresses (the stable address and the link-local one are the
same), and the H.264 encoder's report, which a new boot has only once someone
watches. The kernel's log has the usual boot lines and the driver's loading.

The second, the published `hardened-blikvm-system-0.1.0-beta.3-seq4.tar`
(slot 78's build, `932cea9`), went to that board once it ran slot 78: 6.6
minutes to upload and verify, 35.9 to write and boot
(`raw-system-update-beta3-20261007-install-seq4.json`), and its install was
applied over the reboot the page had left pending, as the fix has it. It came
back with everything the same as above but one thing: QUIC was off. Both
builds name their image `Hardened BliKVM H616 SD image 0.1.0-beta.3
(2026-10-07)`, so the owner took the new root for the one it had recorded
under, followed the board and recorded QUIC off. The image name is the
release and the day of the build: a board going from one release to another
always has another name, and gets its switches back as the first install
showed; one that is given a build of the release it already runs (a second
build of the same day, or the same bundle again) does not. The release notes
say so; telling a replaced root apart from the image name is left for the
next update runtime. QUIC was switched back on through the page's API (the
operator's setting, `quic-enable-after-raw-seq4.txt`), and the system was
confirmed (the floor is now sequence 5).

Root's home outside `.ssh`, which the update does not carry, was kept on the
data partition before each install and put back after (14 entries, the same
digest), the copy removed each time.
